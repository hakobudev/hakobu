Run your projects on servers you own.

A file in your repository says what runs. CI builds each commit; your server pulls the release, swaps it in with no downtime and turns the commit green, or red with the reason. No panel, no database: the file is the state.

Nothing pushes to a server.

CI builds each commit into images and pushes them to a registry. The server checks the release tag every 30 seconds and deploys each new one. CI needs no access to it, and any CI that can push an image works.

  1. Your repositoryhakobu.toml, a Dockerfile per app, sealed secrets
  2. CIhakobu build: each app, then the release image last
  3. A registryghcr.io/you/app:main, or any other
  4. Your serverpulls the release, deploys it, and sets the commit's hakobu/deploy status

The parts that guard your data, written once.

What's different in each project, its file, Dockerfile and migrations, is yours or your agent's to write. Deploys, backups, secrets and alerts are hakobu's, tested once for every project.

Deploys that can't lose data.

Migrations run in the new image while the old one serves. If they fail, nothing changed. A deploy never deletes: what the file drops is kept until a person deletes it.

Secrets in the repository.

Each one sealed with age to the server and to you. Anyone, an agent too, can add one; only the two of you can read it. A diff shows which changed, never a value.

Agents welcome. Data stays a person's.

Each server is its own MCP server, over SSH: an agent sees status and logs, deploys, rolls back and sets a repository up, with a skill for Claude Code. Nothing to install on your laptop. Restoring or deleting data is root's, and a person's at a terminal.

Nothing comes in.

The server pulls its releases, hakobu's own too. You and your agent reach hakobu over SSH, with keys that run its commands and nothing else; its API listens on loopback alone, and the web reaches your apps on 80 and 443 for their own domains, or through a Cloudflare Tunnel with no port open at all. The audit mails you about anything else that listens.

  • Inyou and your agent, over SSH; visitors on 80/443 or a tunnel
  • Outthe registry, your buckets, SMTP, GitHub's commit status and hakobu's releases
  • Elsenothing listens, and the audit checks hourly

Yours, all of it.

hakobu calls no provider's API: no DNS, no cloud, no Git host beyond the commit status. You bring the pieces, and can swap any of them.

  • A Linux serverDebian or Ubuntu, amd64 or arm64. The installer sets up rootless Docker.
  • SSHYour laptop has it: you and your agent reach hakobu through it, and nothing else.
  • A registry and CIghcr.io and GitHub Actions work with no setup.
  • An S3 bucketR2, Hetzner, AWS or any other, for backups.
  • An SMTP accountFor the alerts.
  • Your owner's keyOpens every secret and backup, even without the server. The server makes it, for your password manager.

From a bare server to a green commit.

  1. 1

    A server

    One command; it asks the server's name and how visitors reach your apps (your agent gives them as variables). It ends with the line that gives your agent the server's MCP. After that it updates itself. A server

    $ ssh -t root@203.0.113.7 'curl -fsSL https://hakobu.dev/install.sh | bash'
$ claude mcp add --scope user nova-1 -- \
    ssh -T deploy@203.0.113.7 mcp
  2. 2

    A project

    Ask your agent to set the repository up: it writes hakobu.toml, the workflow and its skill. You type the secrets in your own terminal, sealed on the server; the agent adds them, never seeing one. A project

    you> Set this repository up for hakobu on nova-1.
$ ssh -t nova-1 secret set crm hakobu status_token
you> I sealed the status token; add it and push.
